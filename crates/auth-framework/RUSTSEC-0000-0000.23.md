# JARM JWE did not authenticate its protected header

The AES-256-GCM content encryption of a JARM response JWE was computed without the base64url protected header as additional authenticated data (RFC 7516 sections 5.1 and 5.2, step 14), so a change to the header was not detected when the content was decrypted. The decrypt path accepts only a fixed list of `alg` and `enc` values (RSA-OAEP or RSA-OAEP-256 with A256GCM), so a changed header gave no new algorithm; other header fields (`typ`, `cty`, extra members) could be changed unnoticed by someone able to alter the response in transit. The same omission made these JWEs undecryptable by a standards-compliant implementation, and made this crate unable to decrypt theirs.

Only applications that turn on `enable_jwe_encryption` and build with the `rsa-private-key-ops` feature are affected.

The fixed versions use the protected header as AAD on both encrypt and decrypt. A JWE made by an older version no longer decrypts: there is no fallback, because accepting the old form would keep the header unauthenticated.
